## 1. 这次到底优化了什么

本轮在原产品链上调整了对象职责、依赖和工具行为，保留既有规则、人物身份、存档格式与正式宿主。没有另建自主生活 Runtime，也没有按原型名称把现有系统推翻。

| 原问题 | 优化后 | 对后续开发的作用 |
|---|---|---|
| 观察面板属性会偷偷创建对象 | getter只读，需要创建时显式Ensure | AI审计和调试不会改变场景 |
| 人物准备牌借调试文字所在Canvas | 正式链统一进入PrepCharacterHandRoot | 生成 / 拖拽 / 回手 / 清理共享明确宿主；旧场景兼容仍保留 |
| PrepCardRoot实际是行动牌容器 | 原位更名BattleActionHandRoot | 人与AI可直接辨认人物准备牌和战中行动牌 |
| 老Stage工具可能重装当前绑定 | 五个写入入口显式拒绝，增加只读检查 | 防止用旧初始化器覆盖现有产品场景 |
| 根层级散落大量界面 | 收纳到常驻SceneUIHosts，根对象5个 | 快速找界面，同时保留各自生命周期 |
| 默认名 / 空白名造成误判 | 按用途命名按钮、文字、HUD与部分图片 | 保留原身份与引用，降低观察成本 |
| 已注入长期查询失败后借用临时人物资格 | 配置查询后失败关闭资格回退 | 保护长期Person成长Authority |
| 正式出征初始化借旧MapUI行列 | ExpeditionUI显式持有兼容图参数 | 旧显示层不再控制正式出征初始化 |
| HUD嵌套绑定可能被旧作者化漏掉 | 子树查找并复用，冲突明确拒绝 | 避免重复创建HUD |
| 结算关闭依赖全局固定名字 | 关闭自身子树Canvas | 改名 / inactive时仍定位自身界面 |
| 按钮重复注册或清掉其它监听 | 自身监听幂等管理，结算换绑 / 销毁释放 | 保留Inspector与其他系统监听 |
| 架构散落旧对话、文档滞后 | 19个模块、11个Runtime程序集、8条产品链归位既有两份架构 | 新开发可从仓库恢复当前职责与引用方向 |
| 三份History名字相似 | 明确Producer / Consumer / Identity / 生命周期 / Save链 | 新自主生活设计先审计既有Authority，不凭名称另建账本 |

当前技术路径：

```mermaid
flowchart LR
  Menu[主菜单] --> Town[村庄 / 长期人物]
  Town --> Prep[出征选择与准备]
  Prep --> Journey[Journey表现]
  Journey --> Entry[Progression / Event进入]
  Entry --> Battle[Battle规则与现有UI]
  Battle --> Resolve[当前节点结算]
  Resolve --> Journey
  Resolve --> Return[Return事务]
  Return --> LongTerm[人物 / 村庄长期结果]
  LongTerm --> Save[最终Save]
  Save --> Town
```

图表示现有主产品链的职责分工，不表示每次战斗都立即返乡。规则、状态和视图分离；Battle Victory、RouteCompleted和Return完成是不同状态。

## 7. History Authority Mapping（完整只读调查）

以下保留2026-10-04第15批的专项证据，代码路径相对UnityProject/RRPG1.0game/Assets/Scripts/。原调查未修改Runtime / Save / GameSpec、未动态复现旧档风险；后续第23批全量回归不等于专项旧档风险已解决。

### 1. VillageSocialFactLedger

| 项目 | 当前实现 |
|---|---|
| 定义位置 | `Village/Runtime/VillageSocialFactLedger.cs`；DTO 在 `Village/Runtime/VillageSaveData.cs` |
| 语义职责 | 记录 Person 成功投入 Active Project 的 TemporaryCommitment 动作事实，含项目定义/实例及村庄日期；不记录 Assignment 当前状态、解释、评价或关系 |
| Producer | `VillageRuntimeBridge.TryStartProject` 整批参与者全部成功后写；`TryAddProjectParticipant` 单人成功后写。调用 `RecordTemporaryCommitment`，时间来自既有 Bridge.Time；整批失败回滚不记事实 |
| Consumer | Bridge 的 `CountTemporaryCommitmentsInYear`；`EvaluateDraftBuildupResponse` 读取当年次数，调用 `VillageEventFlow.RaiseRecognition`。产生 Recognition / Pending 不等于事件已执行 |
| Identity Key | `(PersonId, ProjectId)`，重复返回 Duplicate；ProjectDefId 为内容定义，日期不是去重键。当前只有 TemporaryCommitment 类型 |
| 生命周期 | `VillageRuntimeBridge.SocialFacts` 世界级持有；EnsureCore 在 null 时创建；正常追加，不随项目结束删除。Restore 清空后恢复；ResetForTests 清字段 |
| Save Container | `SaveData.Village.Social.Facts[]`，依次对应 VillageSaveData / VillageSocialSaveData / VillageSocialFactSaveData |
| 查询接口 | `Facts`、`CountTemporaryCommitmentsInYear(personId, year)`；私有 ContainsFact 用于判重，没有通用跨类型 Fact 查询接口 |
| Authority 分类 | 当前 TemporaryCommitment 事实的 Source of Record；年内计数为 Derived Query，Recognition / Response 为消费层。不据此认定它是全部自主生活事实的统一 Source of Truth |

保存：`SaveSystem.Save(collection)` → `VillageRuntimeBridge.BuildSaveData()` → `SocialFacts.ToSaveData()` → VillageSaveData.Social → SaveCore / BuildSaveData → SaveData.Village → JsonUtility.ToJson → File.WriteAllText。

加载：`SaveSystem.Load()` → JsonUtility.FromJson → `VillageRuntimeBridge.EnsureInitialized(saveData.Village)` → EnsureCore（Village 非 null 时）→ `SocialFacts.Restore(save.Social)`。过滤空人物/项目、未知类型、非法日期；重复键保留首条；非空 Village 中缺 Social 则为空账本。

兼容风险：**整个 Village 区块缺失**时，EnsureCore(null) 只确保对象存在，不调用 SocialFacts.Restore(null)。首次初始化为空，但已初始化会话内加载无 Village 旧档是否残留已有账本，不能由“旧档默认空”注释保证。本批未动态复现或修复。

### 2. WorldEventHistory

| 项目 | 当前实现 |
|---|---|
| 定义位置 | `Event/WorldEventHistory.cs`；恢复 partial 为 `Event/EventWorldRestoreApis.cs`；所属 EventWorldState 在 `Event/ExpeditionEventSessionState.cs`；DTO 为 `Event/EventWorldSaveData.cs` |
| 语义职责 | 按 EventId 保存累计次数、最近村庄绝对日序、HasLastVillageDay、最近 EventInstanceId。Village / Expedition Domain 均计入；不是逐次完整事件流水或人物人生史 |
| Producer | `EventOptionExecutor.Outcome.cs` 的 RecordHistory：Preflight / Commit 成功后调用 WorldState.History.RecordOccurrence，随后标记 ExecutionState Completed。VillageEventFlow / ExpeditionEventFlow 接入同一 EventRuntimeBridge.World；Resolver 解析不记 occurrence |
| Consumer | `EventConditionEvaluator.World.cs`：EventNotSeen / EventSeenCountAtLeast；`EventResolver.Repeat.cs`：OncePerWorld / VillageDays 冷却；执行 trace 读取提交后次数；EventWorldPersistence.Build 枚举保存 |
| Identity Key | Dictionary 以 EventId 为键，Ordinal 比较；每个定义一条汇总。LastEventInstanceId 只作最近追溯，不是主键或完整去重集合 |
| 生命周期 | `EventRuntimeBridge.World` 世界级持有；EnsureInitialized 在 null 时创建。Restore 先清 History / Flags 后精确恢复，Execution 重建为空。ExpeditionEventSessionState 是独立的一次远征会话记录，不等于世界历史 |
| Save Container | `SaveData.EventWorld.History[]` → EventHistorySaveData。同区块的 Flags / PendingVillageEvent 不是 History 条目 |
| 查询接口 | `OccurrenceCount`、`HasOccurred`、`TryGetLastVillageDayOrdinal`、`HasRecord`、排序后的 `Records`；写入 RecordOccurrence，恢复专用 ClearAll / RestoreRecord / CreateRecord |
| Authority 分类 | 当前世界事件发生汇总与长期重复/冷却查询的正式 Authority；没有从另一份持久化完整日志重建的实现，不能视作可丢弃 Derived View。虽为聚合结构，也不等于通用 Fact Ledger |

**真实保存链已核实**：SaveSystem.Save / SaveWithVillage → SaveCore → BuildSaveData → `EventRuntimeBridge.BuildSaveData()` → `EventWorldPersistence.Build(World, PendingVillageEvent)` → 枚举 World.History.Records → EventWorldSaveData.History → SaveData.EventWorld → JSON / 文件。

加载：SaveSystem.Load → `EventRuntimeBridge.Restore(saveData.EventWorld)` → `EventWorldPersistence.Restore` → History.ClearAll → 对合法条目 RestoreRecord(CreateRecord(...))。精确恢复次数/日期/最近实例，**不调用 RecordOccurrence、不加一**；空 EventWorld 清为空，空 EventId 或非正计数丢弃，重复 EventId 后条覆盖前条。

WorldEventHistory.cs 旧 1B 注释仍写“只读 + 测试种子 / 不进 Save”，与现有 1C 写入口、1D 保存实现不符。结论依据真实代码链，未修改该注释。

防重边界：RecordOccurrence 本身不按 EventInstanceId 去重，依赖 ExecutionState 与产品事务时序；Completed 集合、Expedition Session History 不进入此存档。PendingVillageEvent 保存身份/角色/Context 以保持待处理实例不重抽，不是已发生 History；不能宣称已有跨存档完整 exactly-once 日志。

### 3. PersonLifeHistory

| 项目 | 当前实现 |
|---|---|
| 定义位置 | `Profession/Runtime/PersonLifeHistory.cs`；拥有字段在 `Character/CharacterInstance.cs`；接口为 IFormationHost；DTO 在 `Save/SaveData.cs` |
| 语义职责 | Person-owned 人生事实，实际类型为 ProfessionFormed / ExpeditionReturned；与 FormationState 派生状态分离。不是每日完整经验、Diary 或全世界共享事件日志 |
| Producer | `FormationResolver.cs` 内 **FormationCommitter.Commit** 通过 ActiveProfession / History 判重后追加 ProfessionFormed；FormationResolver.AdvanceDay 调用它。`ExpeditionUI` 返乡链调用 `VillageReturnPersonConsequence.TryCommit` → CommitExperience → 按 PersonId 找长期 Character → AppendExpeditionReturned |
| Consumer | FormationCommitter.HasProfessionFormed 防止再次形成；`UI/ExpeditionPersonIdentity.ResolveExpeditionText` 读取 CountExpeditionReturned / Events，派生次数与最近返回 Outcome；SaveSystem 镜像列表 |
| Identity Key | 容器归属长期 Character.PersonId；条目没有独立 FactId / EventInstanceId / ExpeditionId。Profession 判重为当前人物+ProfessionId；远征条目只有类型/日期/Outcome，不能推导跨会话唯一键 |
| 生命周期 | 每个 CharacterInstance 初始化一份 LifeHistory，跨远征保留。当前 Hero 没有对应人生史提交，返乡明确跳过 Hero。Load 为恢复的 Character 重建列表，缺字段为空 |
| Save Container | `SaveData.Player.Characters[].LifeHistory.Events[]` → PersonLifeHistorySaveData / PersonLifeEventSaveData；所有者 PersonId 在外层 CharacterSaveData |
| 查询接口 | `HasProfessionFormed`、`CountProfessionFormed`、`CountExpeditionReturned`、公开 `Events`；AppendProfessionFormed / AppendExpeditionReturned 自身不判重 |
| Authority 分类 | 当前 Character 已记录人生事实的 Source of Record；FormationState 为不同责任的派生状态；UI 次数/最近 Outcome 为 Derived View。不能假定已覆盖 Hero、Shared Episode、Relationship |

保存：SaveSystem.SaveCore / BuildSaveData 遍历 OwnedCharacters → `SaveLifeHistory(character.LifeHistory)` → CharacterSaveData.LifeHistory → SaveData.Player.Characters → JSON / 文件。

加载：SaveSystem.Load → RestorePlayerCollection → RestoreCharacters → 恢复 PersonId → `RestoreLifeHistory(characterSave.LifeHistory)` → CharacterInstance.LifeHistory。null/缺字段为空；过滤 null 条目/未知 Type，其余逐条镜像，不做日期校验或去重；保存恢复均保留 Outcome，缺 Outcome 默认为 0。

返乡提交在 catch-up 成功后、清 Occupancy 之前、Final Save 之前；取返乡当日 VillageTime。同批 PersonId 去重，ExpeditionRecord.ExperienceCommitted 保证会话内不重复；该标记不持久化。追加不自动写盘，Save 失败重试由既有 Return 流程负责。

### 4. 交叉边界与验证限制

- 三者粒度、键与所有者不同，没有已实现的共同 FactId / Shared Episode Id 或跨容器映射契约。不合并、不另建 Ledger，不为自主生活 Fact 指定归属。
- 社会动作事实 → 年内计数 → Recognition / Pending；Event Option 成功提交 → WorldEventHistory。不得把动作、识别、解析和执行混为同一次记录。
- Facts 为 IReadOnlyList，但事实条目字段可变；PersonLifeHistory.Events 为公开可变 List。追加/只读语义并非完全由类型强制，扩展前仍须审计写入方。
- SaveVersion 当前为 1；文件为 Application.persistentDataPath 下 `rrpg_save_p0.json`。本调查未改变版本、DTO 或存档。
- 已有 VillageSocialFactSaveTests、EventWorldPersistenceTests、ProfessionFormationSaveTests 等测试源码；本批未运行，不把静态追踪当作新往返验证。
- 整个 Village 缺失时的已初始化 Load，以及 NewGame 只新建 PlayerCollection 而世界 Host 的重置责任，列为生命周期风险线索，未复现或顺手修复。

结论：WorldEventHistory 已真实持久化。后续应基于这三份现有语义、所有者与兼容链评估扩展/迁移；自主生活规则、Freeze 与 Product Spec 继续由设计侧定义。
