## 一、生成与覆盖规则

> Current适用说明：生成条件与关闭状态统一服从 [AI开发执行规则](AI开发执行规则.md) §13；本文仅规定 Handoff 格式与事实记录要求。

1. 验证与Acceptance通过后，在任务授权范围内生成Handoff；仅需用户产品判断时取得明确确认，客观任务写验收标准与机器证据。Technical Checkpoint不机械覆盖最终交接。
2. 需要用户验收时可使用“验收通过，收尾。”；含失败项、附加未满足条件或继续修改要求时不生成最终交接。
3. 生成时只更新HANDOFF标记之间内容，保留固定规则；只保存最近真实交接，历史由Git和项目日志承担。
4. 必须实际写入文件、回读HANDOFF并核对diff，不能用聊天报告替代。部分完成/阻塞任务在任务报告中说明。
5. 字段完整填写；无证据写“未记录/未执行/不适用”，不保留“尚未生成”，不猜规则、测试或Git事实。
6. Git Facts记录生成时Local Git / Worktree快照；后续Closure Commit/Push不要求回填未来SHA。没有完成Git核验时不提前写关闭。
7. 完整开发与Closeout流程见执行手册；本文件只维护格式和交接事实。

## 二、状态与证据口径

### 任务状态

记录当前任务实际状态，定义唯一服从执行手册 §13.2 / §13.7：Acceptance Passed 不等于 Work Package Closed、Branch Closed 或 Repository Closed；无 Git 写授权且准备完毕写 Ready for Commit / Push；Push 失败写 Closeout Complete / Push Pending。Handoff 生成时如实记录，不能预宣称未来关闭。

### 验证证据

实现、编译、Console、Unity Play 和用户人工验收必须分别记录，不能互相替代：

- `已实现` 只表示代码或 Editor 配置已落地。
- `编译通过` 只表示本次编译没有新增编译错误。
- `Console 检查通过` 只表示指定时间范围和过滤条件内没有本次新增错误。
- `Unity Play 验证通过` 必须写明实际运行路径和观察结果。
- `用户人工验收通过`须有当前任务明确用户确认，并记录范围；客观任务人工项写“不适用”，不能伪造用户验收。

## 三、Handoff字段与读取边界

### 3.1 固定字段

保持 §五既有结构：基本信息（版本、ID、任务名称、目标、状态、时间、用户验收及范围）、实际变化/影响范围、开发侧验证证据、未验证/遗留/待决策、正式文档影响、Git 事实、完整性声明。验证分别填写实现、编译、Console、Play/Test、用户 Acceptance；Git 事实必须包含基线、**Target Branch**、当前分支、提交 / Push 与工作区的生成时证据。

### 3.2 事实来源

优先读取授权本地工作区中的最新交接；资产副本或旧聊天不能覆盖本地记录。无法取得最新证据时停止对应状态写入，明确缺失；只获得Agent报告时标注“Agent报告”，不得声称独立验证。按文档地图按需读取受影响资料，不默认扫描整个工程。

### 3.3 状态同步与权限

同一开发Agent在Final Closeout中同步任务范围内已确认事实，无需先Feature Commit或独立状态管理员。独立治理任务的“同步本次状态。”窄授权及角色边界见多Agent协议§8；Git授权与详细收尾见执行手册§13。明确文件白名单优先，不因Handoff影响提示获得修改所有正式文档的权限。

### 3.4 Handoff Correction

生成时Git事实正确而后来HEAD变化：保留。交接当时事实写错：由Owner在授权范围内修正并回读；其他Agent先交回Owner协调。若暴露产品缺陷，不能只改交接，按Hard Stop/Reopen边界处理。§五历史事实不得为消除旧流程关键词而改写。
