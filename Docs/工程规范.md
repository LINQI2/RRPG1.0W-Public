# 工程规范

> 状态：Current durable engineering rules。本文只管工程命名、代码组织、Unity 资产与配置制作的长期边界；Agent 权限、工作流、Git、验证与 Closeout 仍服从 [.clinerules.md](../.clinerules.md)、[AI开发执行规则](AI开发执行规则.md)和[AI多Agent开发协作协议](AI多Agent开发协作协议.md)。不以本文修改 GameDesign / GameSpec 玩家规则。

## 命名与职责

- 类型、方法、属性使用 `PascalCase`；局部变量与参数使用 `camelCase`；私有字段使用 `_camelCase`。接口使用 `I` 前缀（如 `IDamageable`）；枚举类型与枚举值使用 `PascalCase`；方法优先以表达动作的动词开头。确实表示事件消息的类型使用 `Event` 后缀。
- 文件名与主要类型一致。代码标识符不用中文或拼音；避免无意义缩写，`UI`、`HP`、`SO` 等项目约定缩写可以保留。
- 名称表达实际职责；`System`、`Resolver`、`Registry`、`Builder`、`Database`、`Catalog`、`Bridge` 等都可在职责吻合时采用，不强制所有类以 `System` 结尾，也不为统一后缀重命名现有类型。
- UI 负责输入与呈现；Gameplay Rule 负责可执行行为；Persistence 负责持久化契约。不要把三者揉成同一权威或让视图状态推导玩家规则。
- 新增或明显扩张系统职责时，应能说明它**负责什么**、**不负责什么**；职责边界不能只靠类名推断。

## 注释

- 核心系统、公共 API 与非显然逻辑在职责、参数、返回值或副作用不显然时，需要简洁注释；优先说明「为什么」和边界，不复述代码字面含义。
- 显然的简单 getter、字段和生命周期方法不制造无意义注释。

## 代码与 Unity

- 不在没有授权时引入新的大型框架或重构公共数据结构。保持组件职责清晰、依赖方向可解释；单文件约 500 行可作为复杂度 **Review Signal**，不是机械拆分的违规 Gate。
- `ScriptableObject` 实例应按其资产/Runtime 职责创建和引用；需要创建时使用正确 Unity API，不得以 `new T()` 创建 SO，当前硬规则服从 [AI开发执行规则](AI开发执行规则.md)中的 `ScriptableObject.CreateInstance<T>()`。不在需要持久资产身份的地方用临时实例替代，也不直接把 SO 写入 Save DTO。
- Unity Scene、Prefab、Inspector 的实际绑定以 Editor 与实际资产为准；Markdown 与代码注释不能代替运行中的资产事实。改变绑定前核对所有引用和生命周期。
- Engine / Project Version 由 README、ProjectSettings 等 Current 事实源承担；本文不维护第二份版本状态或容易过时的全项目目录清单。

## 配置生产与生成物

- 按领域判断制作链。[已迁移 Monster / Enemy Presentation](../Development/Config/README.md) 使用 Authoring XLSX / SourceAssets → Compiler → Canonical Mirror → Unity Builder → Registry / Resolver；生成镜像和 `Assets/Generated/StaticConfig/` 中的资产不得人工编辑。
- 其它未迁移领域须逐域核对现有来源和导入链；不能假设都已迁到新链，也不能把整个工程描述成单一 CSV → Resources SO 或单一 ScriptableObject 配置链。仍采用手工 Resources SO 的领域继续核对既有 `Assets/Resources/ScriptableObjects/`，`_Archive` 不是正式 Authority。
- 配置、运行时对象与表现引用保持分离；人工源、生成物及验证入口见 [Development 导航](../Development/README.md)。
