### R1｜普通 Battle 不采用常规永久死亡

**关联决定**：D-005、D-006、D-012、D-013。

**当前状态 / Authority**：D-012、D-013 有效；Battle 可执行规则以 `GameSpec/Battle/` 为准。

#### 原方案及其要解决的问题

旧方案曾以伤残、Death's Door、普通战斗永久死亡与招募补员承载远征的长期风险。该方案试图让失败具有跨战斗的长期代价，使人口、具体角色、伤残与死亡成为冒险管理的一部分。

#### 发现的问题

当前设计要求 Battle 风险让玩家关心“是谁在承担”，但普通失败不能默认直接变成不可逆淘汰。常规永久死亡会使失败成本过高，容易让玩家只使用最稳阵容与最稳 Build，压缩六人组合和卡牌构筑的实验空间；旧“伤残 → 普通战斗永久死亡 → 招募补员”也不再适合作为当前远征核心循环。

> **制作人于 2026-09-04 补录的设计动机：**常规 Battle 永久死亡容易使玩家把长期认识和塑造的具体人物视作战斗消耗品 / 炮灰，与 Person-first、长期共同生活和人物人生连续性的核心幻想产生冲突。此句是制作人后续补录的 rationale，不是对早期仓库原文的转述。

#### 当前决定

- 普通 Battle 不默认产生永久死亡；0HP 与全员失能按 D-012 及当前 Battle GameSpec 处理。
- 普通失败优先是 recoverable setback，而不是默认毁坏长期成长。
- 当前风险由 HP 跨战、Retreat / Defeat、Run 收益损失，以及后续 Person / Village / History 后果共同承担；具体损失规则以已冻结规格和未冻结边界为准。
- 如果未来设计长期或永久损失，应属于明确、可预期、特殊内容级风险，不得从 Legacy 自动恢复为普通 Battle 的默认淘汰机制。

#### 保留的设计基因

失败必须有后果，并改变后续决策；人物风险仍应落在可识别的具体人物与共同体历史上。被替代的是“普通 Battle 默认永久淘汰”这一承载方式，不是风险、损失和人物重量本身。

#### 未冻结与重新审视条件

仍未冻结：人物完整生命周期、自然寿终正式规则、非普通 Battle 的特殊永久损失、其它长期离场机制，以及 Retreat / Defeat 的正式损失比例与长期健康映射。

只有在未来存在明确、可预期、特殊内容级风险，并能证明不会恢复普通 Battle 的常规淘汰循环时，才可重新审视永久损失的具体形式；任何重审仍需新的正式设计决定与 GameSpec 更新。

### R2｜Person / Assignment / Stable Identity 职责分离

**当前状态 / Authority**：Person、Assignment 与稳定长期身份的职责分离属于 Confirmed Architecture；Formation 基础规则已是 Current Rule，可执行 Authority 见 [Person Current GameSpec](../GameSpec/Person/Person-Profession-Growth-GameSpec-V0.1.md) §12。正式命名、职业内容、数值、阈值、Duration、Transition、Dormant、Trait 效果及 Hero 联动仍未冻结；设计边界见 `GameDesign/04 Person.md`与`GameDesign/当前设计状态.md`。

#### 要解决的问题与发现的问题

RRPG 需要让一个长期生活、积累 Life History 的具体 Person 最终形成能够影响 Battle Expression 的稳定角色身份。Assignment 只描述人物当前在做什么；若当前岗位直接覆盖长期身份，身份会随短期调度高频跳变，无法概括真实人生。反过来，若长期身份形成后永久固定、完全不受后来显著人生方向影响，也无法继续忠实表达人物历史。

> **解释性例子：**今天种田、明天打铁，不应导致人物身份瞬时跟随岗位跳变。该句用于解释 `Assignment ≠ Profession`，不是历史文档原句；原始设计证据中的对应表达是 `Farm ≠ Farmer Factory`。

#### 当前决定

- Person 是长期连续存在并积累 Life History 的具体人物。
- Assignment 只描述当前职责 / 当前投入。
- Assignment 与稳定长期身份不得一一映射；当前岗位不得自动改写人物永久身份。
- 稳定身份应来自真实、长期的人生实践，而不是由一次 Assignment、一次事件或玩家直接写入结果。
- 身份形成后应具有较高稳定性，不随 Assignment 高频变化。
- 长期且显著的新人生方向未来可以支持身份改变；过去经历继续保留在 Life History，不因身份变化被抹除。

#### 保留的设计基因

玩家塑造环境、机会、训练、工作和生活轨迹，但不直接生产人物最终会成为谁；稳定身份是人生的高浓度表达，并最终连接 Battle，而不是岗位标签或菜单选择。

#### Supporting Candidate、未冻结与重新审视条件

`Profession` 的正式命名与内容模型仍是 Supporting Candidate；这不否定已经 Current 的 Formation 基础规则。

仍未冻结：最终命名、正式职业内容、Formation 数值与阈值、Duration、Experience / World Fact 的正式内容及权重、Transition、Dormant、Profession Trait 具体效果与数值，以及具体卡牌 / Hero 联动。不得以这些未冻结细节笼统否定 Current Formation 基础。

进入正式 Formation / Stable Identity 内容与系统设计时，必须基于真实 Life History 来源和实际消费者重新核对 `Profession` 模型；不得把测试 Hook、经验条、隐藏评分、Tag 权重或当前岗位自动升级为 Formation 规则。

### R3｜V3 从 Trend Runtime 转向 Fact-first Social Response

**当前状态 / Authority**：Fact-first Social Response 与“Trend 不是 V3 必需 Runtime System”属于当前已采用方向；设计 Authority 见 `GameDesign/当前设计状态.md`，可执行边界见 `GameSpec/Village/Village-GameSpec-V0.1.md` 第 5 章。

#### 原方案及其要解决的问题

旧 Village V0.1 曾把 Trend 作为 State Change 与 Event / Consequence 之间的结构化状态。Trend 可以增长、下降、组合多个来源并参与 Event 条件，用于让长期行为积累为可感知的社会变化。旧规格没有规定所有 Event 都只能由单一阈值触发。

旧概念链近似为：

```text
Behavior → State Change → Trend → Event → Choice → Consequence → New State
```

#### 发现的问题

把 Trend 预设为统一 Runtime 中间层会过早抽象社会状态，容易把长期变化压缩成隐藏程度条，并诱导建立 Satisfaction、Social Pressure、Mood、Opinion 等万能社会指标；在真实消费者尚未出现前，这会扩大 Runtime 与持久化结构，却不能保证反馈来自合理人物或真正改变玩家决策。

#### 当前决定

V3 使用 Fact-first Social Response：

```text
World Fact / Experience
→ Pattern
→ Observer
→ Recognition
→ Signal / Event / Response
→ New Decision
```

核心原则是：

> **No Observer → No Social Response**

Experience 记录相对客观的长期事实；Pattern 表示事实形成了可识别的长期模式；Observer / Recognition 负责说明谁注意到了、为何有资格认识；只有在值得玩家处理时才进入 Signal、Event、Response 与 Consequence。

被否决的是“Trend 必须成为统一 Runtime 中间层”，不是自然语言意义上的长期趋势本身。Pattern、Observer、Recognition、Signal 是设计语义与职责边界，也不要求分别建立独立 Runtime System。

#### 保留的设计基因

长期行为必须能够积累、被解释并改变未来决策；社会变化应有可追溯来源，重大长期模式应可被玩家感知。V3 的变化是延后统一数据抽象，并补上 Observer / Recognition，而不是取消历史积累与长期趋势。

#### 未冻结与重新审视条件

仍未冻结：Pattern 具体算法、重复次数或时间窗口、Observer 选择算法、Signal / Event 内容、Community-level 状态是否结构化、正式 UI / 场景表现，以及 Trend 是否最终成为正式 Runtime System。

只有未来出现多个稳定消费者，反复需要共享统一 Pattern 数据层时，才重新评估是否抽象正式 Trend Runtime；在此之前不得为便利而预建万能社会指标或统一程度条。

### R4｜RRPG Static Configuration Production Architecture（D-019）

> **2026-09-23 实施注记：** 下文“Production Migration 尚未开始”保留 D-019 决策当日口径；现在 Monster Definition / Enemy Presentation 的 M0–M4 波次已落地，Monster Legacy 已于 M4 退休。其它领域仍按现行实现逐域判断，不能从首波完成推断全域迁移。

**Decision Status（当前）**：**Target Architecture 已确认**（长期静态配置生产架构的方向与分层），本决定只冻结架构方向与边界，不改变任何 Gameplay Rule 或 Save 原则。

#### Authoring Authority

长期静态内容制作主要采用：

```text
XLSX
+
Source Assets（按内容需要）
```

- **XLSX 是制作人主要人工 Authoring Authority。**
- **Source Art 是 Source Assets 的已验证子类。** T4 Spike 直接实证的是
  `PNG Source Art → Managed Sprite → Visual Asset Catalog → Runtime`。
- Prefab / AudioClip / Material 可以保留为 Selected Target Pattern 的**扩展对象**，
  但这些对象类型**尚未逐类完成 Spike 实证**，**不得**写成「全部已经验证」。
- **纯数值 / 纯文本 Static Configuration 不要求存在 Source Assets。**
- Generated JSON / MD / C# / SO / Catalog / Config Database / Asset Manifest **都不得成为第二套人工 Authority**。
- 静态配置必须可由 Authoring Source **确定性重建**。

#### 适用范围（D-019 只管什么）

D-019 适用于 **producer/content-authored、data-driven static configuration**。

**不得**推出：

- 所有技术常量都必须放进 XLSX；
- Schema grammar 必须由 XLSX 定义；
- 测试 Fixture 必须进正式 Workbook；
- Gameplay Rule Authority 转移给配置表；
- 程序语义由表格决定。

配置可以承载 **Gameplay Parameter**，但参数的**游戏语义 / Rule Authority 仍服从 GameSpec 与对应系统 Authority**。

#### Build Pipeline

长期目标链：

```text
XLSX + Source Assets
        ↓

        ↓
Canonical JSON / Asset Manifest
        ↓
Unity-specific Builder
        ├─ Aggregate Config Database
        ├─ Presentation Database（按需要）

Gameplay Consumer
```

**依赖方向**：Gameplay **只能**依赖稳定的 Definition / Registry 契约；**不得**反向依赖 XLSX、Config Compiler、Editor Builder 或 `AssetDatabase`。Runtime **不得**要求 `AssetDatabase` 或 Editor assembly。

#### Runtime Representation

对于 **XLSX-authored pure static configuration**，默认目标 Runtime Representation 是：

```text
Aggregate Config Asset / Database
```

**而不是**：

```text
per-entry ScriptableObject
```

Canonical JSON 的主要职责是：

- Git Review；
- AI 读取；
- CI 校验；
- Debug；
- Unity Builder 输入；
- 确定性重建证据。

**它不是人工编辑源。**

##### Canonical Mirror 的 Git 策略（本决定冻结，不再 Not Frozen）

**Canonical JSON + deterministic Asset Manifest 默认作为 `Generated Review Mirror` 进入 Git。**

硬边界：

- **不允许人工编辑**；
- **不成为第二 Authoring Authority**；
- **必须能从 XLSX / Source metadata 确定性重建**；
- Build / CI 应能**检测 mirror 与 Authoring 不同步**。

**不进入 Git 的执行态内容**：

- latest `BuildReport`；
- `.build-state`；
- `.build-tmp`；
- 临时日志；
- 机器本地执行状态。

**Generated Unity runtime assets（Config Database / Presentation Database / Asset Catalog / Managed Unity Assets）
是否进入 Git，本轮继续 Not Frozen**，交给 Migration FDS 决定。

Runtime JSON 已由 Spike 证明可行，保留为 **Valid Fallback**，但**不作为当前默认主路径**。

#### Unity Object

Sprite / Prefab / AudioClip / Material 等 `UnityEngine.Object`：

```text
stable AssetId
    → generated Unity Asset Catalog
    → UnityEngine.Object
```

**不得**要求制作人长期手工维护 Inspector Catalog 引用、Catalog Size、`.meta` / GUID，或逐项拖拽资源。

**对象类型边界**：Spike A 直接实证的是 **Sprite**（`PNG Source Art → Managed Sprite → Visual Asset Catalog → Runtime`）。
Prefab / AudioClip / Material 属同一 Pattern 的**扩展对象**，**尚未逐类完成 Spike 实证**，不得写成「全部已验证」。

#### Legacy Target

以下**不再作为未来目标架构**：

- `Resources.LoadAll`；
- God `DataManager`；
- 大量 per-entry SO 作为 XLSX-authored pure static config 的默认表示。

但：**Current Product Implementation 在 Migration 前继续保留。**

D-019 **不授权**：删除 `DataManager`、删除现有 SO、删除 CSV、重接 Gameplay Consumer。

#### Save Boundary

静态配置架构改变**不得**改变长期 Save 原则：

- Save 继续保存：**稳定 ID + 长期运行结果**；
- **不得**保存：ScriptableObject 对象引用，或 Generated Runtime Object 引用。

#### Schema / Workbook Principle（已由 Spike 验证）

- Machine Field = 字段身份 Authority；
- 物理列位置无业务语义；
- 中文 Header 不参与机器身份；
- A 列可做人类说明且不导出；
- `ignore` / `note` 列不导出；
- 已有字段可重排；
- 新增真正 Gameplay 字段属于 **Schema Evolution**；
- Child Sheet 用于不定长 1:N；
- XLSX 为 binary Authoring，Canonical JSON 是其 text mirror。

#### Producer Principle

正式目标是让制作人只需要：

```text
配置表 + Source Assets + 一键 Build
```

不需要：

- 手工复制 JSON；
- 手工维护 Catalog Size；
- 手工拖 Sprite；
- 理解 `.meta` / GUID；
- 逐阶段执行脚本。

**实现形式不冻结**：`RRPG_*.cmd`、PowerShell、未来 Editor Window / GUI、具体文件名与路径，
**都不是 D-019 的冻结内容**。正式 Producer UX 形态继续 **Deferred to Migration / Production Rollout**。
制作人的正常目标保持为：**配置表 + Source Assets + 单一 Build Action**。

#### 架构边界（配置架构不拥有什么）

配置架构只负责 Static Configuration 的 **Authoring / Build / Representation / Lookup**。

**不拥有**：Gameplay Rule、Runtime State、Person Identity、Battle State、Expedition State、Village Simulation、Save Authority。配置改变**不能**推翻这些 Authority。

- 所有领域具体 Sheet Schema；
- enum Authority 最终形式；
- 每种内容是否都使用同一个 Database；
- Database 按领域拆分还是聚合的最终粒度；
- 是否采用 Addressables；
- Mod / Hot Update；
- 多平台优化策略；
- 正式美术资产目录最终命名；
- Producer UI 最终形态；
- Migration 波次的最终数量；
- 正式配置性能优化细节；
- **Generated Unity Runtime Artifacts 的正式入库策略（Config Database / Presentation Database / Asset Catalog / Managed Unity Assets 是否进入 Git）**；
- **Config Compiler 最终实现技术 / packaging / distribution 形式**。
