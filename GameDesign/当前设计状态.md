## 一、本轮核心定义变化

RRPG 的当前顶层定义已从旧“Rogue 角色构筑卡牌 RPG”调整为：

> 单人长期共同体经营 + 远征式 RPG 卡牌构筑。

核心关注对象是具体人物与持续变化的共同体。战斗 / 远征负责 Run 随机构筑、人物风险与短期后果；人物长期系统负责 Starter、Unlocked Pool、Trait 与成长阶段；村庄负责塑造未来条件和社会选择。

完整概念、核心幻想、八条 Design Pillars 与非目标见 [01 产品定位与设计支柱.md](01%20产品定位与设计支柱.md)。

Battle 规则切版已在设计轨完成。当前可执行 Battle 规则唯一入口为 [GameSpec/Battle/](../GameSpec/Battle/)。

GameDesign 的 Battle、Person、Cards 与 Expedition 文件只保留体验职责和跨领域设计边界，不复制共享行动力、抽牌、距离、Intent、状态结算或 Scene / UI Binding 细则。

设计轨归位本身不证明实现完成；当前实现与 Legacy Implementation 状态由项目状态快照、代码及 Unity Editor 判断。

本次 Battle 内容归位（以下为设计状态说明，不新增 Freeze 分类，不授权开发）：

- **Current Design Principle**：Enemy 应为人物、卡牌和空间构筑制造新的决策，不能只是血量或数值检查；归位于 [03 Battle](03%20Battle.md) §3.6，具体玩家规则仍服从 Battle GameSpec。
- **Deferred / Not Frozen**：普通敌人分类、精英敌人、Boss 阶段与机制、敌方是否使用牌或拥有行动力、特殊的不完全可预测机制、敌人组合逻辑、难度增长与属性曲线。
- **Deferred UX Candidate**：上次队伍快捷选择、推荐阵容；不代表固定小队。
- **Deferred / Not Frozen**：特殊 Encounter 是否覆盖通常上阵人数上限，见 [06 Expedition](06%20Expedition.md)。
- **未来跨系统候选 / Not Frozen**：Battle 是否产生重伤、Village 资源变化或更广泛 World Fact；不是 Current 输出或已实现事实。
- **Not Frozen**：英雄最终是否进入普通 Profession 体系，既不确认进入，也不确认排除。

### 2026-09-17 Battle × Expedition Product Model 归位同步

以下为 2026-09-17 制作人已确认结果的最小归位说明；详细规则仍以各专项 Authority 为准，本文件不复制规则正文。

- **Battle 空间**：Player 与 Enemy 各自拥有独立 3×3 逻辑 Board；两边共享同一种 Row / Column 空间语言，但 **Occupancy 与 Adjacency 各自独立**，敌我可以同时占据各自 Board 的相同 `(Row, Column)`。Authority：`GameSpec/Battle/Battle-GameSpec-V0.1.md` R5.0 / R5.1 / R5.3.3 / R6.3。
- **Card 顶层类别**：只有角色牌（Character Card）与通用牌（Common Card）两类；独立 Item Card / Item Deck / Item Hand / TP / Item Selection 产品模型已退出，药剂、炸弹、工具等物件内容只是 Common Card 的内容表现。Authority：Battle GameSpec §7、`05 Cards.md`。
- **Expedition 节点**：Shop / Recruit / Rest 不是固定地图 Node 生态要求；若未来存在，属于某个 Node Content / Situation 中可能出现的服务或机会，正式 Node Content Pool 仍未冻结。Authority：`GameSpec/Expedition/Expedition-Progression-GameSpec-V0.1.md` §2 / §15 / §16。
- **Hero**：最低产品身份已确认——独立产品层级 / 玩家自身与主角载体；Battle 中按正常战斗单位的空间、位置、目标与占位规则参与。Hero 完整成长、与 Profession 的最终关系、独有资源、村庄职责与跨存档结构仍 **Not Frozen**。Authority：`04 Person.md` §4.7 / §4.8。

以上是 2026-09-17 的设计归位记录，不作为今天的实现状态声明；双 Board 与 Legacy 迁移的实时结果应从 Docs 状态文档、代码与 Unity Editor 核对。

### 2026-09-18 Expedition Journey Presentation 归位同步

以下为 2026-09-18 制作人已确认结果的最小归位说明；详细规则仍以各专项 Authority 为准，本文件不复制规则正文。

- **Current Presentation Contract**：Expedition 玩家层默认表现为队伍向右旅行；Encounter 自动中断；完成后返回 Journey。
- **Continue 保留**：`继续前进` = 跳过当前旅行表现并抵达下一次 Presentation 边界；多个合法后继时只能跳到 Branch，不自动代选。
- **Presentation 与 Rule 分离**：Pause / 可选 Speed-up / Skip 均只影响表现；现实播放时间不产生 elapsed days、Supply、HP、VillageTime 或其它规则变化。
- **Single-transition Presentation Cycle**：一次 Journey Presentation Cycle 最多消费一个 Progression Transition；完成后必须重新读取 Current Progression State，再决定下一轮 Journey / Branch / Encounter 表现，禁止旧 callback 连续吞后续 Node。
- **Current Rule 保留**：Node、0/1/N 后继、Branch、Supply、elapsed days、Battle 接入、Return / Retreat 与 V4F Return 全部继续服从 Expedition Current GameSpec。
- **第一版兼容**：Current 有限 Graph 可以继续作为后台 Progression 来源；Legacy 完整节点图不作为玩家层默认表现。
- **长期 Strong Direction**：主模式倾向无限远征，但 Encounter Pool、生成算法、Biome、终止条件与正式内容尚未冻结，WP-E 不实现。
- **人物连续性**：Journey 队伍复用准确 `PersonId`；Current 冻结的是 `PersonId → exact Person → Presentation Visual` 解析契约，不冻结 Catalog / Profile / Sprite / Animator / Spine 等具体视觉数据架构；不建立第二套 Party、Person 或 Visual Identity Authority。

Authority：`GameDesign/06 Expedition.md` §6.2A、`GameSpec/Expedition/Expedition-Progression-GameSpec-V0.1.md` §17、`Docs/决策记录.md` D-017。

### 2026-09-25 Enemy Encounter Generation 归位同步

以下为制作人已确认的敌方遭遇生成当前方向；WP-Encounter-1（1A → 1C-R）已按此实施并由制作人完成产品链人工验收。本文件只记录设计语义与 Freeze 边界，不复制配置表字段正文与实现细节。

- **Current 方向**：普通 Battle **不再**按关卡逐场固定手配敌人，也**不再**从全 Monster Pool 无结构独立随机；Current 为 `Encounter Template（遭遇模板）+ Composition Slot（组合需求位）+ Monster Classification（怪物分类）+ Constraint / Threat（约束 / 威胁）→ Generated EnemyRoster（生成敌方阵容）`，并保留**固定怪 + 条件随机怪混合配置**能力。
- **怪物分类**：威胁值 / 级别（Tier）/ 基础随机权重来自怪物遭遇画像；战斗定位（Melee / Ranged / Tank / Support）可一怪多行。
- **约束范围**：`Require` / `AnyOf` / `Exclude` × `Role` / `Tier` / `MonsterId`，加上威胁预算区间；同种怪是否允许重复由遭遇控制。敌人数量的唯一来源是组合需求位的数量区间。
- **空间**：敌方 Board 最多 **9** 只（3 排 × 3 列）；站位模式 `Any` / `Row` / `Exact`；排内视觉规则 1 人居中 / 2 人左右 / 3 人左中右。
- **身份分离**：`EnemyInstanceId`（本场实例身份，战斗单位与 UI 卡名使用）≠ `MonsterId`（模板身份：名称 / 数值 / 美术 / AI 规则）。
- **Not Frozen（不得据此实现）**：正式 Encounter 内容与平衡、正式 Node → EncounterPool 内容绑定、Species / Allegiance / Biome、Encounter Modifier / Curse、正式 Elite / Boss 内容、无限远征正式 Depth 模型、正式错误 UI，以及生成算法的最终形态与候选扩展维度。

Authority：`Docs/决策记录.md` D-020、[WP-Encounter-1 Closeout Report](../Docs/DevelopmentSpecs/2026-09-25_RRPG_WP-Encounter-1-Enemy-Encounter-Generation-Foundation-Closeout-Report-V0.1.md)；当前可执行配置与实现入口见 [Development/Config README](../Development/Config/README.md) 与代码。Battle / Expedition 的体验职责与既有未冻结边界仍见 03 Battle / 06 Expedition，本文件不复制其正文。


### 2026-09-26 Unified Event Content Foundation 归位同步

以下为 2026-09-26 制作人人工验收 PASS 后的最小归位说明；详细规则仍以 FDS / Closeout Report 为准，本文件不复制规则正文。

- **Current 方向**：Event 内容（Trigger / Role / Condition / Presentation / Option / Outcome / Effect）由 `EventId → Event static config` 唯一决定；`NodeId` 与 Legacy Catalog **不是** Formal Event Authority。
- **两表面一致**：Village 弹窗与 Expedition Journey 卡共用同一 `EventTemplateRenderer` 与同一 `EventPresentation` 文本入口；插图只走 `IllustrationAssetId → 共享 VisualAsset Authority`（失效时明确诊断 + 类别级占位图，绝不换图）。
- **表现与规则分离（冻结）**：**Presentation progression follows Product progression**——任何 Node Entry 失败（补给不足 / 解析失败 / 生成失败 …）都不得推进 Journey 表现（不消费 Cycle、不跳节点、不自动重试、不生成后续卡面）；Battle / Prep 未结束前不得出现新的 Branch / 正式 Event 卡。
- **结算语义**：Event Node 必须「Resolve 成功后才 Enter」；额外时间经既有Event效果入口转换为分钟累计，Legacy字段不成为第二Clock，Node Settlement 统一结算并 exactly-once 消耗 Supply；Event StartBattle 的 Preflight / Commit 使用**同一份** `EnemyRoster`，Victory / Defeat 结算**同一个** Node。
- **Not Frozen（不得据此设计正式内容）**：正式 Event 内容 / 数值 / 文本 / 美术、Event 结果反馈表现（如「储备口粮」`+2 → 时间 −2` 的中间反馈）、ChoiceHistory、Event 队列 / Deadline / 惩罚 / 多事件并发、Village Modal 插图宿主。

Authority：[WP-Event-1 FDS](../Docs/DevelopmentSpecs/2026-09-26_RRPG_WP-Event-1-Unified-Event-Content-Foundation-FDS-V0.1.md) §21.9–§21.14、[WP-Event-1 Closeout Report](../Docs/DevelopmentSpecs/2026-09-26_RRPG_WP-Event-1-Unified-Event-Content-Foundation-Closeout-Report-V0.1.md)、`Docs/决策记录.md` D-021。

## 三、人物长期成长状态

当前已经归位的设计语义：

- Run 内只累计 Pending ProfessionExp，不写长期；Return 时统一提交已产生的 ProfessionExp，Normal Return 包含主动撤退和有限路线完成后的返回，Expedition Failure 也完整保留已产生的 ProfessionExp。该规则只适用于 ProfessionExp；金币、材料等其他收益的保留和损失规则仍未冻结，不得泛化为失败时所有收益都保留。Authority 见 [Person Current GameSpec](../GameSpec/Person/Person-Profession-Growth-GameSpec-V0.1.md) §10；
- 达到条件后由玩家主动逐级升级，可以延后；
- 等级是成长阶段，不自动提高基础 HP、Attack 或 Range；
- 初始 Starter Slot 为 1；
- 普通攻击是可占用 Starter Slot 的正常角色牌；
- 1 个 Slot 提供 1 张 Run 起始副本，允许重复模板占用多个 Slot；
- Starter 只在长期成长机会中调整；
- Unlocked Pool 同时服务长期成长与 Run 奖励候选；
- Trait 是具体人物唯一的专属被动，可强化但不普通替换；
- 当前 Starter 可以积累熟练，换出后高级熟练不永久保存。

`Base Trunk × Person Life Architecture Concept Checkpoint V0.1` 保存该轮讨论证据；用户已采用“人物的长期人生最终形成某种稳定角色身份，并影响 Battle Expression”及 `Assignment ≠ Profession`，两者归类为 **Confirmed Architecture**。Person / Profession / Growth / Run-Return Experience 的可执行规则已于 2026-09-06 归位到 [GameSpec/Person/](../GameSpec/Person/README.md)：PersonId = 具体人物稳定实例身份（CharacterId / HeroId = 静态模板身份）；Assignment ≠ Profession；普通 Person 当前阶段允许无 Profession 或 1 个 Active Profession（active-state 约束，多职业 / Dormant 正式结构仍未冻结）；当前 Trait 归位为 Profession Trait（不存在当前正式的独立 Person-specific battle Trait）；Level 是职业战斗成长阶段、不自动增加基础属性；Full Card Pool 与 Person Unlocked Pool 分离；Run 内 Pending 经验在 Return 统一写长期（Normal Return 含主动撤退与有限关卡完成；Expedition Failure 也保留；第一版不额外给 Completion 经验）。

`Profession` 的 **Formation 基础规则**已于同日归位 Current（见 [GameSpec/Person/](../GameSpec/Person/Person-Profession-Growth-GameSpec-V0.1.md) §12）：无 Active Profession 的 Person 经长期真实生活、工作与事件经历，其职业身份达到成熟稳定后自动 Formation（不要求玩家点击确认）；Formation 按日结算，由统一 Strength / Qualification / Candidate / Target / Stability Resolver 决定；Evidence 只来自真实经历，Assignment 不等于 Evidence；Life Direction Event 只提供大额 Evidence、不得直接写 Active Profession；首次 Formation 的 Initial Pool / Starter / Trait Definition 属 Profession Template 共享配置；M6 不实现自动转职、Dormant 与 Transition。

`Profession` 的 **Formation 数值与正式内容模型**保持 Supporting Candidate / Not Frozen：Formation Strength 数值尺度、Qualification 阈值、Candidate 滞后、Dominance / Stability 参数、Long Ambiguity 触发时长、Talent / Family / Ability 正式系统、Future Transition、最终命名、正式职业内容、正式经验曲线与正式 Trait 数值均未冻结。

经验曲线、Slot 上限、熟练数值、稳定身份的 Formation 与最终命名、Profession Trait 的具体效果与数值、多职业 / Dormant 正式结构和人物经历正式机制仍未冻结。英雄最低产品身份已确认（独立产品层级 / 玩家自身与主角载体，见 §二 2026-09-17 同步与 [04 Person.md](04%20Person.md) §4.8）；Hero 完整成长、Profession 关系、独有资源、村庄职责与跨存档结构继续保留为专项设计入口，不得从旧英雄规则自动恢复。

## 四、村庄设计状态

村庄已从旧功能建筑列表提升为长期共同体经营层。

当前宏观与中层设计已经确认：

- 总体循环：塑造条件 → 组织行动 → 远征 → 承担结果 → 安全返程与消化 → 世界变化；
- 村庄循环：观察 → 选择优先级 → 作出承诺 → 推进时间 → 后果显现；
- 实时推进、暂停、加速与跳至重要时间节点的时间方向；
- 长期世界事实经由可感知过程被共同体回应并影响后续决策（不预设 Trend 为必需 Runtime System，见本节 V3 Social Response 当前方向）；
- 村庄通过扩大未来可能性连接人物与 Battle；
- 八个社会决策维度与“现在 ↔ 未来”“谁受益 ↔ 谁承担”两个横切轴；
- 五层社会复杂度阶梯；
- 团结 ↔ 发展、信仰 ↔ 知识是没有唯一正确答案的辩证主题。

Theme 总体结构是 Tree / Branch，不是线性文明塔；五层阶梯只表达理解与内容教学复杂度，不是 Theme 解锁顺序、DLC 前置链或唯一历史发展路线。

Food 是 Minimal Survival Constraint 的首选测试承载，FP-V0.1 最小 Ingredients → Food 链按 Resource GameSpec 读取，不代表最终全量资源冻结。资源链与时间等已有 Current Rule 按各自 GameSpec 读取；2026-10-07 有限 Building Foundation 已归位 Current。建筑正式内容、完整经济、政策 / 文化与所有正式数值仍未冻结。

### V3 Social Response 当前方向

`V3 Social Response Concept Checkpoint V0.1` 已批准，[Village-GameSpec-V0.1](../GameSpec/Village/Village-GameSpec-V0.1.md) 第 5 章已按此同步。当前方向：

- V3 承担 **History → Social Meaning**：让长期治理被具体人物与共同体感知、表达并影响后续决策，Village 不是沉默的人力机器；
- **Observer / Recognition 是必要职责边界**：`No Observer → No Social Response`；Experience（客观事实）≠ Recognition（人物当前认识）≠ Event（值得玩家处理）；Response ≠ Complaint，Consequence ≠ Penalty；
- **Pattern / Observer / Recognition / Signal 是设计语义与职责边界**，不要求分别建立独立 Runtime System 或对应持久化结构；V3 优先复用现有 World Fact / Person / History / Event 数据；
- **Trend 不是 V3 必需 Runtime System**，V3 也不建立 Satisfaction / Social Pressure / Opinion / Mood 等万能社会指标；是否抽象为正式 Trend System 后置决定；
- **V3 Minimal Runtime 不依赖 Minimum Village World Integration**：回应可用 UI / 文本表达，World 世界化 Social Surface 为后续增强，不构成 V3 前置条件；
- **V3 Closure 至少证明一次完整决策回环**：Past → Recognition → Response → New Decision → New Future（长期事实 → 可感知回应 → 后续决策发生变化）。

### Minimum Village World Integration 当前方向（第一包边界，2026-09-04 制作人裁决）

制作人已批准进入第一 bounded World Work Package 的设计边界（只批准职责，不冻结实现）。归位后的 Current 内容：

- **第一证明目标**：Person 在 Village World 中具有可识别 Presence；Assignment / Active Project 能锚定到最小 Place；一个真实 Project 完成后 World 留下可持久化的可见痕迹；Save / Load 后该痕迹仍存在。
- **职责分工**：World 负责 Presence / Place Anchor / Persistent World Change 的最小空间承载；UI 继续负责治理（Roster、Assignment、Project、Social Response 与其它现有管理面板）。

- **实现候选全部未冻结**：Place Registry 类名 / 数据结构、Place 类型命名、Scene 布局与 Camera / Layer 承载、坐标存储、Marker / Primitive / 色块等表现、Tooltip / 点击交互、全部正式美术（Supporting Candidate / Test / Not Frozen）。

## 五、社会复杂度框架

当前内容复杂度按以下理解顺序积累：

1. 共同体形成：团结与发展；
2. 内部秩序：冲突、规则与治理；
3. 共同体边界：警戒与外部关系；
4. 共同价值：信仰、意义与文化；
5. 认知与挑战：知识、质疑与方法。

这不是正式篇章表，也不是 Theme Tree 的线性解锁表。篇章数量、名称与边界仍未冻结，后续内容也不应清零前一层已经建立的系统关系。

## 六、已被替代或降级

### 已被当前设计替代

- 角色为核心、卡牌只是辅助的顶层定义；
- 普通战斗永久死亡作为核心循环；
- 旧个人行动力 + TP 与 Death's Door 设计；
- 角色升级获得 HP / Attack 属性点；
- 永久保存整套 Run Build；
- 角色牌作为上阵凭证、独立旧道具牌堆；
- 固定 16 + 16 卡牌承载；
- 固定 4×3 点阵地图与固定 Shop / Recruit / Rest / Boss 地图节点生态（Shop / Recruit / Rest 若未来存在属于 Node Content 设计，不作为固定节点类别要求）。

### 降级为 Legacy / Historical Candidate

- A1-A4 / B1-B4：保留为历史内容母题，不保留旧套牌结构；
- 食物、木材、石材、金币四资源；

- 旧 PvP 结构。

### Deferred：跨存档 Meta Progression

同一 Village World 内跨多次 Expedition 保留的人物、共同体和长期可能性，**不等于跨存档 Meta Progression**。旧全局声望、英雄声望、声望解锁英雄或套牌都不属于 Current Rule，也不得因旧文件或实现仍存在而恢复。跨存档 Meta 是否存在仍为 Deferred / Design Frontier；不建立 Meta GameSpec。

未来若重开这项设计，先回答：它为重复游玩提供什么体验；怎样与具体 Village World / Person 隔离；是扩大起始可能性还是带来永久数值优势；是否削弱具体人物和共同体的长期塑形；在 New Game、Failure 与多档之间如何表现。未回答前不冻结解锁表、数值或实现范围。
