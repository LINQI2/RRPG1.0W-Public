# RRPG｜Identity 角色设计方法论 v0.6（仓库对齐候选）

**内容基线：2026-09-16；导航修订：2026-09-17**  
**Freeze Level：Supporting Candidate**  
**性质：角色设计方法 / Supporting Tool / 非 Current Rule Authority**  
**适用阶段：RRPG 当前角色（Identity / 工程字段 Profession）Battle 内容设计阶段**  
**来源：Farmer、Hunter、Cook、Worker、Herbalist 五轮角色设计实践 + 2026-09-16 构筑体验与组合体验研究**

> **产品概念优先使用 Identity（身份）。** 当前工程与旧文档仍大量使用 `Profession` 字段；本方法论只在引用工程/旧字段时保留 `Profession`，不再把“职业”作为产品概念边界。

## 0. 一句话核心

> **先确定“这个人为什么会因为长期人生而以不同方式理解战局”，再建立母题与子题地图，用少量验证样例证明它们真的能玩；通过全局 Gate 后再进入正式具体实现。多个内容开始互相重新估值时识别 Build Seed，并同时检查单体、组合、Shared Deck 与 Encounter 中的体验如何建立、放大、成型与兑现；最后再安排 Placement、Starter、Trait、初始池与后续语言包。**

这套方法主要解决两件事：

1. 角色为什么不同、玩家在思考什么不同的问题；
2. 这些策略结构为什么最终会形成值得期待、成型、放大和兑现的构筑体验。

## 1. 使用边界

### 1.1 不负责重新设计 Village
Identity 的世界合法性、形成经历、生活来源属于上游输入。当前角色设计阶段默认上游已经回答“这个人为什么会活成这种人”。

角色设计负责：
> **这种人生进入 Battle 后，玩家会怎样不同地思考和行动。**

如果上游身份信息不足，可以回查或询问制作人；不要擅自扩张 Village、社会、经济系统。

### 1.2 不是机械 SOP
- 某一步不适用时可以跳过；
- Trait 可以先做，也可以后置反推；
- 初始池不要求固定张数；
- 子题数量不要求对称；
- 一个母题可以暂时只展开一个子题；
- 没有自然内容时允许留空；
- 不要为了模板完整强行造机制。

### 1.3 方法论低于 Current Rule
Current Rule / 已冻结规则必须遵守；本方法论只用于思考、展开、筛选、验证和收口。方法论若与最新制作人决策冲突，以制作人决策为准。

### 1.4 仓库 Authority 与术语兼容

- 本方法位于 `GameDesign/Identity/`，只服务角色内容设计；
- [GameSpec/Person/](../../GameSpec/Person/README.md) 负责 Profession / Formation / Growth / Starter / Trait / Pool 的 Current Rule；
- [GameSpec/Battle/](../../GameSpec/Battle/README.md) 负责 Battle Fact、目标、行动资源、空间与卡牌行为；
- `Identity` 是本轮产品设计术语，**不等于已经把 Current Rule / Runtime 的 `Profession` 正式改名**；
- `Strong Candidate` / `Stage Design Closure` 只是置信度或阶段标签，不是 Freeze Level；
- 本轮具体角色、卡牌、Trait、Build 默认 `Concept / Not Fully Frozen`，直到制作人明确采用并按仓库治理归位。

## 2. 快速参考：完整设计链

```text
Identity 上游输入
↓
Battle Identity（战斗身份核心）
↓
母题地图
↓
子题 / 玩家问题地图
↓
验证样例（Proof Sample）
  └─ 每个重要子题只用少量具体实现证明“能玩”
↓
母题 / 子题全局 Gate
  ├─ 是否重叠
  ├─ 是否伪子题
  ├─ 是否缺关键方向
  └─ 是否仍被同一个 Battle Identity 统一解释
↓
正式具体实现
↓
局部零件替换与问题诊断
↓
Build Seed 开始形成
  ├─ 内生 Seed：主要由同一 Identity 内部内容形成
  └─ 涌现 Seed：由多个 Identity / 通用牌 / Trait / Battle Fact / Encounter 自然形成
↓
构筑体验层（多尺度）
  ├─ 自身体验
  ├─ Identity × Identity 组合体验
  ├─ Identity × Shared Deck / 系统杠杆体验
  └─ Build × Encounter 环境兑现体验
↓
优势曲线 / 体验发动机 / 放大轴
↓
建立 → 放大 → 成型 → 兑现 → 收尾
↓
内容 Placement（出现阶段 / 认知复杂度）
↓
Starter / Trait / Initial Pool / 后续语言包
↓
Shared Deck 开放性与组合依赖 Gate
↓
Prototype（原型）验证
↓
Battle Language 候选回灌
↓
Strong Candidate（当前唯一默认候选）收口
```

> 这是一条**检查链**，不是要求灵感严格按顺序产生。Card、Trait、Battle Fact 或组合灵感都可以提前出现；但正式收口前必须回到相应层级验收。

> **验证样例 ≠ 正式内容。**  
> 验证样例只负责证明某个母题 / 子题能否落地；只有整体策略地图通过 Gate 后，才系统进入正式具体实现与 Build Seed 设计。

## 3. Identity 与 Battle Identity

### 3.1 Identity 不是 Battle Role
Identity 不等于 Tank / DPS / Healer / Support。Battle Role 只是某个 Build 最终形成的投影。

优先问：
> **这个 Person 因为长期生活经历，习惯怎样认识和处理战局？**

而不是：
> “现在队伍缺什么岗位？”

### 3.2 Identity 上游输入
至少理解：
- 这个身份为什么在世界中成立；
- 主要形成经历；
- 这个身份长期反复接触什么经验；
- 哪些是人格，哪些是身份经验；
- 是否有需要特别注意的 Village / Person 上游约束。

### 3.3 Battle Identity
Battle Identity 不是技能列表，而是：
> **玩家使用这个身份时，会反复以什么方式重新理解正常 Battle Fact？**

当前已形成方向示例：
- Farmer：促成并经营成长过程；
- Hunter：识别并捕获机会；
- Cook：料理已有价值，提高当前使用效率；
- Worker：让共同作业不断档 / 主动补结构缺口；
- Herbalist 当前候选：判断什么处理在什么状态下才正确。

## 4. 母题

母题是：
> **一个身份长期人生经验进入 Battle 后，能够持续生成多个不同玩家问题的根。**

母题应尽量满足：
1. 来自身份长期经验，而不是临时技能幻想；
2. 能反复产生不同玩家问题；
3. 能容纳不同 Battle Operation；
4. 不依赖唯一专属资源才成立；
5. 不只是某个数值或 Battle Fact 的名字；
6. 不是人格标签；
7. 未来可以长出多个具体实现，但不要求现在全部证明。

层级：
```text
Identity
↓
母题
↓
子题
↓
具体实现
↓
零件 / 数值
```

> **越往上层，否定所需证据越高。**

一个 `+3 Damage` 不好玩，优先说明具体实现或零件有问题，不能直接推出整个母题不成立。

---

## 5. 子题 / 玩家问题

### 5.1 子题不是 Battle Fact 分类
不要机械拆成“HP子题 / Status子题 / Position子题”。

真正的子题必须对应不同玩家问题。

例如 Herbalist：
- 轻重缓急：**有多严重，因此值得投入多少、采用什么处理？**
- 因症施治：**到底是什么问题，因此应采用什么处理？**

区别来自玩家判断，不是字段名。

### 5.2 不要制造伪子题
以下通常不能直接升成子题：
- 参数变化；
- 单个 Battle Fact；
- Timing 变化；
- “承上 / 启下”这类同一问题的触发方向；
- Count；
- 单纯不同 Operation；
- 为了表格对称强补的概念。

### 5.3 子题数量不要求对称
母题A有2个子题、母题B只有1个完全可以。设计目标不是表格整齐，而是玩家问题真实存在。

## 6. 验证样例与正式具体实现

### 6.1 先用验证样例证明“子题能玩”

在母题 / 子题地图阶段，可以提前写少量 Card / Trait / Operation 样例，但它们首先属于：

> **Proof Sample（验证样例）**

用途是回答：

- 这个子题是否真的能产生不同玩家问题？
- 它是否只是换了一个 Battle Fact 或数值？
- 两个看似不同的子题能否通过具体规则保持差异？
- 这个方向能否在不扩张大量新系统的情况下成立？

默认每个重要子题 **1～2 个验证样例即可**。  
不要在子题尚未完成时沿一个样例一路做成整套牌池。

### 6.2 母题 / 子题全局 Gate

验证样例完成后，先横向检查：

1. 子题之间是否实质重叠；
2. 是否存在伪子题；
3. 是否遗漏身份真正重要的玩家问题；
4. 所有母题是否仍被同一个 Battle Identity 统一解释；
5. 哪些子题已强成立，哪些只需保留为待验证候选。

Gate 通过后才进入正式内容生产。

### 6.3 正式具体实现是当前可验证方案，不是唯一答案
母题 / 子题必须通过具体规则证明它真的能玩，但任何 Concrete Sample 都只是当前可验证方案。

### 6.4 机制方案族（Mechanic Schema Family）不再是必经层
旧流程曾使用：
```text
母题 → 子题 → Schema Family → Concrete Sample
```

当前修正为：
```text
母题 → 子题 / 玩家问题 → 具体实现
```

如果多个具体实现后来共享稳定规则骨架，可以**事后**归纳为 Schema Family 用于整理。

> **Schema Family 是归档工具，不是设计前置步骤。**

### 6.5 优先公共战斗语言（Battle Language）
优先从已有语言寻找表达：Attack / Damage、HP、Shield、AP、Draw / Card / Hand、Position、Adjacency、Status、Retain、Card Owner、Intent、临时牌等。

不要为了身份感立刻发明专属资源。

### 6.6 相同效果操作（Operation）≠ 角色重叠
多个 Identity 可以使用同一公共零件。真正判断是否重复，要比较：
- 读取什么；
- 为什么读取；
- 玩家在做什么判断；
- 谁主动改变结构；
- Trigger；
- Target；
- Time / Frequency；
- 最终系统职责。

## 7. 局部零件替换与问题诊断

正确顺序：
```text
具体实现
↓
发现明确问题
↓
定位问题来自哪里
↓
只替换最小零件
↓
重新验证
```

常见可替换零件：
- Trigger
- Observation
- Target
- Operation
- Time
- Frequency
- Duration
- Value
- Range
- Owner
- Position / Adjacency
- Card Type / Cost
- 临时牌 / 正式牌
- 是否选择 / 自动目标
- 是否读取 History

### 7.1 选择预算
额外主动选择会同时增加控制权、稳定性、信息质量和泛化性，因此选择本身是一种高权限零件。

如果随机、自动目标、最高/最低、当前目标已经能表达身份，不要无意义增加二次选择。

如果“选谁”就是牌的核心玩家问题，例如 Worker《换岗》选择与谁交换位置，则属于合法核心决策。

### 7.2 泛化性预算
“任意 Card / 任意效果 / 任意属性”拥有更高权限，越泛化越容易吃掉未来设计空间。

### 7.3 读 Fact ≠ 改 Fact
身份很多时候只需要反复关注某种 Fact，不需要每次都修改它。不要为了显得特殊就频繁改 Cost / Type / Owner / Target / Effect 本体。

## 8. 认知复杂度与内容阶段（Placement）

### 8.1 复杂度必须看具体实现和零件
不能仅凭母题或子题判断“复杂 / 不复杂”。同一子题可以拥有简单初期实现和复杂后期实现。

### 8.2 当前事实（Current Fact）与历史事实（History Fact）的认知成本不同
Worker 实践新增经验：
> **需要玩家回忆“刚才发生过什么”的 History Fact，本身就是额外认知预算。**

例如：
- Previous Owner；
- Acted This Turn；
- Previous Target。

它们并非禁止使用，但初期高密度出现会要求玩家持续维护脑内历史缓存。

因此初期默认更优先当前可直接观察的 Fact，例如 HP、Position、Adjacency、Intent、Hand、Status。

> **History 不是“必须后期”的硬规则，而是一个应单独计入的复杂度零件。**

### 8.3 初期内容不负责展示完整 Identity
初始阶段可以只展示身份最简单的一层问题。

职业成长不仅可以表现为数值增强，也可以表现为：
> **玩家逐渐学会这个身份更深的一层思考方式。**

### 8.4 第一场战斗不强制有构筑
一个角色只有一张起始牌也可以合法运行。构筑应随着远征中的卡牌获得、卡槽扩展、人物增加逐步发生。

## 9. 构筑种子（Build Seed）

### 9.1 构筑种子不默认属于单一 Identity

当一组 Battle 内容开始：

- 持续互相重新估值；
- 形成可以成长的玩法方向；
- 出现“建立 → 放大 → 成型”的潜力；

即可视为 Build Seed。

这些内容可以来自：

- 同一 Identity 的 Card / Trait；
- 多个 Identity；
- 通用牌；
- Position / Adjacency / Status 等公共 Battle Fact；
- 敌人和 Encounter 条件。

> **Build 属于这次 Shared Deck / 战斗结构，不天然属于某个职业。**

### 9.2 两类构筑种子

**内生 Seed**

主要由一个 Identity 内部内容自然形成。

例如：

> Herbalist 的“透支 → 调理 → 再透支”。

**涌现 Seed**

单个 Identity 内部并不存在完整路线，但多个开放接口组合后自然产生。

例如概念上：

> Worker 改变 Position / Adjacency  
> → 创造新的空间机会  
> → Hunter 捕获该机会。

这个 Build 不需要被命名为“Worker 流派”或“Hunter 流派”。

### 9.3 构筑接口（Build Interface）

设计 Identity 时不只看“它自己有哪些牌”，还要看它向 Shared Deck 提供什么开放接口。

接口通常是：

- 它经常读取 / 改变哪些公共 Battle Fact；
- 哪些资源会被它重新估值；
- 哪些状态或结构会因为它存在而变得更有价值；
- 它能否让别的 Identity / Card 出现新的最优使用方式。

当前五个案例的理论接口示例：

- Farmer：Growth / 培养 / 延迟兑现；
- Hunter：Opportunity / Timing / Target；
- Cook：Card / Hand / Cost / 使用效率；
- Worker：Position / Adjacency / 独狼 / 群羊 / 结构重组；
- Herbalist：HP / Status / 风险 / 恢复 / 身体资源转化。

这些只是分析抓手，不是新的职业分类。

### 9.4 构筑种子最低检查

至少问：

1. 玩家围绕什么问题构筑？
2. 哪些内容正在互相重新估值？
3. 它是内生 Seed 还是涌现 Seed？
4. 哪条优势可能被逐渐放大？
5. 它是否依赖固定 Identity Combo 才能成立？
6. 如果移除某个 Identity，剩余内容是否仍各自具备最低玩法价值？

## 10. 构筑体验层：必须做多尺度审查

> **构筑体验层不是独立方法，也不是角色设计起点。**
>
> 它只在 Identity / 母题 / 子题 / 正式具体实现开始形成 Build Seed 之后使用。

顶层锚点：

> **玩家亲手建立一条越来越可感知的优势曲线，并看到自己、组合关系或整个 Shared Deck 因构筑而发生质变。**

### 10.1 体验不能只孤立看 Identity 自己

RRPG 使用 Shared Deck，因此至少从四个尺度审查体验：

#### A. 自身体验
这个 Identity 自己让玩家获得什么独特感受？

例如：
- Farmer：价值被养大；
- Hunter：抓准机会；
- Worker：重构空间关系。

#### B. Identity × Identity 组合体验
两个身份同时存在后，是否通过公共 Battle Language 自然重新估值彼此？

目标不是预制 Combo，而是：

> **各自独立成立，组合后出现新的决策价值。**

#### C. Identity × Shared Deck / 系统杠杆体验
这个 Identity 加入以后，是否让大量原有 Card / Trait / Battle Fact 重新估值？

例如 Worker 的移动本身可能数值很小，但一次 Position 变化可以同时改变：

- Adjacency；
- 独狼 / 群羊；
- 多张空间条件牌；
- 多个 Trait；
- 后续行动路径。

> **爽感的承载主体不一定是角色自身收益，也可以是它对整个系统产生的杠杆作用。**

#### D. Build × Encounter 环境兑现
这套体验在什么敌人、压力和战场环境里才能真正成立？

例如：
- Hunter 需要有可识别的机会窗口；
- Worker 需要空间关系真的影响牌与 Trait；
- Herbalist 需要身体压力 / Status / 风险能够进入决策。

不要仅在真空牌表中判断 Build 是否好玩。

### 10.2 三条基础优势曲线

**扩张**：我方有效能力越来越大。  
体验：“我越来越大 / 越来越能做事。”

**压缩**：战场对我的有效威胁越来越少。  
体验：“敌人越来越拿我没办法。”

**稳定**：Build 的波动、风险和崩溃概率越来越低。  
体验：“以前我要赌，现在我已经稳了。”

“这局已经成了 / 基本不会输了”通常是上述曲线积累后的成型状态，不单独作为第四条基础曲线。

### 10.3 组合体验不要求每个角色自己拥有显眼爆点

一个 Identity 可以主要通过：

- 自身成长；
- 帮其他内容兑现；
- 重构 Shared Deck；
- 提高系统灵活性；
- 创造新的决策空间；

产生体验价值。

因此不要仅用：

> “这个角色自己能不能打出大数字 / 自己有没有闭环”

评价角色是否有爽点。

## 11. 体验发动机

发动机回答：
> **优势为什么会越来越大？**

当前7个核心发动机：

- **EN-ACC｜积累**：一个已有价值持续堆高；
- **EN-MUL｜倍增 / 高频**：一份价值复制成更多份；
- **EN-LOOP｜循环**：输出重新生成下一轮输入；
- **EN-CHAIN｜连锁**：A触发B，B再触发C，向外传播；
- **EN-CONV｜转化**：一种资源转换成另一种价值；
- **EN-SUP｜压制**：主动降低战场有效威胁；
- **EN-STB｜稳定**：持续抵消不利变化，提高下限、一致性和容错。

> 一个 Build 不需要全有；一个 Identity 也不需要覆盖全部发动机。

Damage / 击杀推进是 PvE 最重要的终端价值出口之一，但不是唯一爽感来源。

## 12. 放大轴

常用放大轴：
- 幅度；
- 频率；
- 范围；
- 数量；
- 持续时间；
- 效率；
- 稳定性；
- 覆盖率；
- 传播深度；
- 容错。

因此：
- 群伤不是独立发动机，而是范围轴；
- 大数字不是发动机，而是幅度结果；
- DoT 往往是时间 / 持续兑现方式；
- 连击常见为倍增/高频发动机 + 频率轴。

---

## 13. 体验弧线

```text
建立
↓
放大
↓
成型
↓
兑现
↓
收尾
```

### 建立 / 张力
玩家为了启动 Build 需要付出什么？例如 AP、HP、时间、卡槽、站位、随机、机会成本、短期弱势。

### 放大
沿什么轴越来越明显？

### 成型拐点（Breakpoint）
玩家什么时候第一次产生：
> **“成了。”**

### 兑现（Payoff）
玩家最终明显看到什么？例如巨大 Damage、高频攻击、全场 AOE、连锁爆发、长循环、敌方威胁失效、999 Shield、资源永续。

### 收尾（Closure）
PvE 中要检查：
> **Build 已经明显赢定以后，还需要重复多少无意义操作？**

偏防御、控制、无限资源、永续恢复的 Build 尤其要避免过长垃圾时间。

---

## 14. 体验调制器与反馈

体验调制器不是发动机，但会改变体验味道：
- 风险；
- 随机；
- 精准条件；
- 延迟验证；
- 创造性；
- 稀缺性。

反馈表现：
- 数字；
- UI；
- 状态层数；
- 动画；
- 音效；
- 节奏；
- Hit Stop；
- 连锁提示；
- 成型提示；
- 威胁被压制后的明显反馈。

> **机制成立 ≠ 爽感自动成立。**

例如10次伤害如果瞬间合成一个“20”，高频爽感可能消失。

---

## 15. 起始牌 / Trait / 初始牌池 / 成长

### 起始牌（Starter）
不需要表达身份最深哲学，优先用最低复杂度教玩家第一层玩家问题。

### Attack / Damage
Attack / Damage 是非常好用的公共零件：
- 反馈直接；
- 成长明显；
- 易形成爽感；
- 易与其它发动机发生转化。

但不要因此把所有 Identity 设计成直接输出职业。辅助、防御、控制、资源效果应结合具体 Build 环境判断其如何影响胜利推进。

### Trait
允许：
- Trait-first；
- Cards-first；
- Trait / Card Co-design。

若过早 Trait 会把所有牌吸向单一玩法，可以先做 Card，再从真实动作中反推 Trait。

### 初始牌池（Initial Pool）
不要求固定张数。没有自然内容就不为数量强补。

---

## 16. Shared Deck、开放构筑接口与组合 Gate

### 16.1 Identity 必须先独立成立

不要设计成：

> 没有另一个指定 Identity 就无法运行。

Identity 自己应至少拥有：

- 清楚的玩家问题；
- 最低可玩表达；
- 不依赖指定队友的基础价值。

### 16.2 组合关系的三级 Gate

组合体验按依赖程度分为：

**Level 1｜独立成立**

A 自己能玩，B 自己也能玩。

**Level 2｜自然增值（目标状态）**

A 的存在让 B 的部分 Card / Trait / Battle Fact 重新估值，反之亦然。

核心是：

> **1 + 1 > 2**

而不是卡面直接写“队伍中存在某职业时”。

**Level 3｜强制依赖（谨慎）**

没有 A，B 的核心玩法基本失效。

默认谨慎使用，除非未来产品明确需要强组合结构。

### 16.3 低职业耦合，高机制互操作

Shared Deck 的组合价值优先来自：

- 公共 Battle Fact；
- 公开资源；
- Position / Adjacency；
- HP / Status；
- Card / Hand / Cost；
- Timing / Target；
- 其它可被不同 Identity 共同读取或改变的语言。

而不是：

> Farmer 专用 Cook Buff  
> Hunter 专用 Worker Combo

### 16.4 不把 Shared Deck 做成多套职业小卡组简单相加

错误方向：

> 每个 Identity 内部已经完全闭环，别人只是锦上添花。

更理想的是：

> **Identity 自己能成立，同时保留足够开放接口，让其它 Identity 改变它的估值。**

这为涌现 Build Seed 提供空间。

### 16.5 重复 Identity 必须考虑

不能默认 Farmer / Hunter / Cook 各一人。

允许：
- Farmer + Farmer；
- Worker + Worker；
- 同身份不同 Person。

如果玩法只有“标准职业队”才成立，说明可能隐藏了固定配队结构。

---

## 17. Battle Language 候选回灌

角色可以暴露新 Battle Fact，但不要一发现就公共化。

推荐流程：
```text
某个具体实现需要新 Fact
↓
先记录为局部设计需求
↓
看是否有多个独立内容反复需要
↓
评估认知 / UI / 规则成本
↓
再决定是否提升为公共 Battle Language
```

一张 Card 需要 Previous Owner，不意味着马上建立全项目 History 系统。

---

## 18. 强候选（Strong Candidate）收口

一个设计阶段如果要结束，原则上应留下一个默认继续验证的具体方案。

可以：
- 未冻结；
- 数值待调；
- Trait 待后置；
- 某张牌留空；
- Prototype 后继续修改。

不要无必要停在“A / B 都行”。

---

## 19. 反向禁区（Anti-Gate）

1. **不要从体验发动机反推 Identity。**
2. **不是每张 Card 都必须独立拥有发动机。**
3. **不是每个 Identity 都要覆盖7种发动机。**
4. **不要为了“爽”强行指数爆炸。**
5. **不要把 PvP Anti-fun 直接搬进 RRPG PvE。**
6. **不要为了模板完整强行补母题、子题、Trait、首池张数。**
7. **不要把 Schema Family 当必经层。**
8. **不要因为一个验证样例失败就否定高层母题。**
9. **不要在子题地图尚未完成时，把验证样例误当正式内容一路做成 Build。**
10. **不要只孤立评价 Identity 自身收益；必须检查组合与系统杠杆。**
11. **不要因为理论组合很漂亮，就反向写固定职业 Combo。**
12. **不要要求每个 Identity 都拥有固定数量的“内部流派”。**
13. **不要把 Build Seed 默认归属于单一 Identity；保护 Shared Deck 的涌现构筑。**
14. **不要让当前程序实现反向限制尚未冻结的玩法设计。**

PvE 更应该问：
- 机制是否过早杀死玩家自己的决策空间？
- 敌人与关卡是否还能提出新问题？
- 成型以后是否进入过长垃圾时间？

---

## 20. 构筑种子阶段验收十二问

### 身份 / 策略层
1. **这个 Identity 让玩家思考什么独特问题？**
2. **母题 / 子题是否仍由身份人生经验支撑？**
3. **正式具体实现是否真正证明了子题，而不是只换数值？**

### 构筑体验层
4. **这条 Seed 是内生的，还是由多个内容涌现出来的？**
5. **主要优势曲线是什么？**
6. **优势通过什么发动机增长？**
7. **玩家什么时候第一次感觉“成了”？**
8. **成型以后怎样明显兑现？**
9. **优势建立以后怎样避免无意义收尾？**

### 组合 / 系统层
10. **它在 Identity × Identity / Shared Deck 中会让哪些内容重新估值？**
11. **组合属于“自然增值”还是已经滑向“强制依赖”？**
12. **当前 Encounter 是否真的能让这套体验成立，而不是只在纸面成立？**

如果前3问答不上：Identity / 策略层还没立住。  
如果4～9问答不上：可能理论合理，但还没有真正的 Build 体验。  
如果10～12问答不上：可能单体成立，但 Shared Deck / Encounter 体验尚未被证明。

## 21. 当前方法论状态（2026-09-16）

### 已被多角色实践反复验证
- Identity 先于 Battle Role；
- 母题 → 子题 → 具体实现；
- 越高层越谨慎淘汰；
- 问题出现才换零件；
- 选择预算；
- 泛化性预算；
- 读 Fact ≠ 改 Fact；
- 相同 Operation ≠ 角色重叠；
- Trait / Card 权重不固定；
- Initial ≠ Full Identity；
- 公共 Battle Language 优先；
- 低职业耦合、高机制互操作。

### Worker 新增 / 强化
- History Fact 读取本身属于额外认知复杂度预算；
- Battle Fact 先局部验证，再考虑公共化；
- 同一母题可以通过 Placement 在成长中分阶段开放。

### 2026-09-16 新增候选体验层
- 3条基础优势曲线：扩张 / 压缩 / 稳定；
- 7类体验发动机：积累 / 倍增 / 循环 / 连锁 / 转化 / 压制 / 稳定；
- 体验弧线：建立 → 放大 → 成型 → 兑现 → 收尾；
- Damage / 击杀推进是 PvE 重要终端价值出口之一，但不是唯一爽感来源；
- 体验层服务角色设计，不独立反向定义 Identity。

### 2026-09-16 五 Identity 实践新增
- 子题阶段采用“批量铺地图 → 少量验证样例 → 全局 Gate → 正式内容”，不再逐子题无限纵向下钻；
- Build Seed 可分为内生 Seed 与涌现 Seed，且不默认属于单一 Identity；
- 体验层扩展为多尺度审查：自身、Identity×Identity、Identity×Shared Deck / 系统杠杆、Build×Encounter；
- Identity 应提供开放构筑接口，使其它内容自然重新估值；
- 组合优先追求“各自独立成立 + 组合后自然增值”，谨慎强制依赖；
- Shared Deck 不应退化为多套职业小卡组简单相加；
- Identity 的爽感承载主体可以是自身，也可以是它对整个战场 / Deck 产生的结构杠杆。

## 24. 当前不是最终版

本方法论仍然是：
> **Supporting Candidate / 软方法。**
